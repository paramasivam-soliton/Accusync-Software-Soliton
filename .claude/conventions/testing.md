# Testing convention

- **Framework:** xUnit + Moq.
- **File/class naming:** source `Foo.cs` → test file `FooTests.cs`, test class `FooTests`. The file name matches the class name (standard .NET convention) — not the source file's own name. Exception: a persistence-layer repository split across the two test regimes below uses `FooTests.cs`/`FooTests` for the mocked majority and a second `FooConstraintTests.cs`/`FooConstraintTests` for the real-database constraint tests.
- **Method naming:** `MethodUnderTest_Scenario_ExpectedOutcome` — the method being tested, the precondition/input, and the expected outcome, each a PascalCase segment joined by underscores. This is the Given/When/Then structure in substance (precondition → action → outcome), but don't spell out the literal words "Given"/"When"/"Then" — they're redundant noise once the three segments already carry that meaning. E.g. `Parse_ScreenerProfileId_ReturnsScreener`, not `GivenTheScreenerProfileId_WhenParsed_ThenReturnsScreener`. No `Test1`, no abbreviations. Keep the `ExpectedOutcome` segment to the single primary outcome — don't bolt on a second clause justifying or qualifying it (e.g. `WithoutTouchingOtherFields`, `InsteadOfX`) when that's already evident from reading the test body; if a secondary assertion genuinely needs to be called out, that's what the test body and its assertions are for, not the identifier.
- **Body structure:** no `// Arrange`/`// Act`/`// Assert` section comments and no inline comments explaining what an assertion (or a setup step) is checking — a descriptive test name (see Method naming) already carries that context. If a test needs a comment to be understood, the name isn't descriptive enough; fix the name instead of adding a comment.
- **Naming inside the test:** the system under test is named after the class it exercises, not a generic `sut`/`_sut` — e.g. `_userService` in `UserServiceTests`, `userContext` in `CurrentUserContextTests`. A field when it's constructed once in the constructor and reused; a local when each test constructs its own (e.g. via a `CreateXxx()` helper). Mocks are `_xxxRepositoryMock` (or similar), typed `Mock<T>`.
- **What to mock:** only real boundaries — repositories, external I/O, adapters. Keep pure-logic collaborators (e.g. a hasher, a policy) real in the test so it verifies actual behavior, not "the mock returned what it was told to." When a test class mixes real + mocked dependencies, say why in the class `<summary>`.
- **Persistence-layer tests:** mock `IDbContextFactory<T>`/`DbContext`/`DbSet<T>` (Moq + `MockQueryable.Moq` for the async LINQ surface — `ToListAsync`/`FirstOrDefaultAsync`/etc.) rather than running against a real database; this keeps the suite fast and lets every branch (not just the ones a real schema happens to reject) be simulated directly. Exception — stay on a real in-memory SQLite connection (`Database.EnsureCreated()`, no migration history, via a `TestDbContextFactory`) instead, for either of:
  - A test whose entire point is verifying that the database itself enforces a constraint (a unique-index collision, a NOT NULL column, a foreign-key violation) — a mock told to throw doesn't prove the schema actually enforces anything.
  - A repository whose behavior genuinely depends on EF's own query translation rather than the repository's own code — DB-generated keys (`ValueGeneratedOnAdd`, needed so a later `GetByIdAsync(entity.Id)` in the same test resolves), multi-level `Include`/`ThenInclude` chains, correlated-subquery search filters, or `Skip`/`Take` paging math. Reproducing these faithfully in a hand-rolled mock (e.g. simulating auto-increment key assignment) adds more test-only risk than it removes — a class can stay entirely on this regime rather than being split.

  Say which regime a test class/method uses and why in its `<summary>`.
- **One behavior per test.** Multiple `Assert` calls are fine if they're all confirming the same outcome (e.g. a list and its contents).
- **No skipped/ignored tests without a comment** stating why and what would need to happen to re-enable it.
- **Layout:** test project structure mirrors source 1:1 — `Tests/{ProjectName}/{same folder path as source}`.
