# Clean code convention (C#)

- **XML doc `<summary>`** required on every public type and member in `Core`/`Application` — classes, constructors, methods, properties, no exceptions. When using a primary constructor for DI, document each constructor parameter with `<param>`.
- A method implementing an interface member must carry at least `<inheritdoc/>` if it has no doc of its own. Give it a real `<summary>` instead only when there's implementation-specific detail worth stating beyond the interface's contract (e.g. a concrete storage format) — don't duplicate the interface's wording verbatim.
- Summaries explain domain rules/invariants in plain engineering language. Never cite JIRA ticket IDs, "User Story"/epic names, spec-doc section numbers, or `FEATURE_REQUIREMENTS.md` — see [feature-requirement.md](feature-requirement.md).
- Summaries must be precise — short and exact, not padded with detail the signature already gives.
- No long inline comments. Inline `//` comments explain *why*, never restate the next line.
- Never put an inline comment next to a method call explaining what that method does — that explanation belongs in the method's own `<summary>`, not at the call site.
- TODOs are fine but must describe the concrete gap and a direction for resolving it, not just "fix this later."
- One blank line between a property/method and the next one's summary block — never stack a summary directly against the previous member's closing brace.
- Standard file header on every `.cs` file: the existing `<copyright file="X.cs" company="Natus Sensory">` block.
- Expected failure paths return a dedicated `XResult` type (`Success`/`ErrorMessage`/...); exceptions are reserved for truly unexpected conditions, not control flow.
- User-facing strings go through the generated `Strings.{Class}_{Case}` resource keys, never raw literals.
- **Primary constructors for DI-only classes** — a class whose constructor body would otherwise contain nothing but dependency-to-field assignments (e.g. `AuthenticationService`). Reference each parameter directly by its camelCase name in the class body; don't also declare a `private readonly` field for it. This applies uniformly across every project (`Application`, `EF`, `Presentation` ViewModels, etc.) — no project or layer is exempt.
- A constructor that does anything beyond storing dependencies — wiring up an `ICommand`, seeding a collection or default value, kicking off fire-and-forget async work, validating an argument — stays a standard constructor with explicit `private readonly` fields and PascalCase/camelCase naming, even though its parameters are still plain DI (e.g. `LoginViewModel`, `ChangePasswordViewModel`). Don't mix the two styles on one class — a class with any non-DI constructor logic uses a standard constructor for all of its dependencies, not just the ones tied to that logic.
- Always use braces/code blocks for `if`/`else`/`for`/`foreach`/`while`, even a single-statement body (e.g. a guard clause `return`). No single-line `if (x) return;` — it hurts readability. Applies to new code and to existing code touched incidentally while editing nearby.
- **Member ordering by visibility:** within a class, order members private-first, then protected, then public. Concretely: a private field with no matching public property — a constructor-injected dependency, or plain internal state — goes in its own block at the top of the class, followed by the constructor; public properties/events/commands/methods come after that. A private field that is the dedicated backing store for one of the class's own public properties is the one exception: it stays directly above that property instead, wherever the property naturally falls (the common ViewModel idiom — this pairing is not a violation, and isn't pulled up into the top-of-class private block). (See `InactivityTimer`: `_currentUserContext`/`_timer` — DI dependencies with no property — sit at the top above the constructor, with `DefaultIdleTimeout`/`SessionExpired` after.) Applies to every file in every PR, including existing code touched incidentally while editing nearby.
- Always consult the conventions under `.claude/conventions/` (via `CLAUDE.md`) before and while writing code — don't rely on general C# habits where a project convention exists.
